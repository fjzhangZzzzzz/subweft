# 新版配置编辑器性能报告

测试日期：2026-10-30。对象：ADR-0008 单配置编辑器 0.2.0-dev。

**结论：普通家庭规模表现良好；大配置叠加历史版本时存在明显瓶颈，需要在扩大使用规模前优化。** 1,800 次设备下载全部成功且内容摘要一致，60 次原生检查和发布成功；但压力档 30 并发下载 P95 达 8.82 秒，不能把零错误率等同于性能合格。本次仅测试和分析，未修改业务实现或生产。

## 环境与方法

- Windows 11 Pro 10.0.26300，Intel Core Ultra 7 255H，16 核/16 逻辑处理器，可见内存 31.43 GiB。Go 1.27.3，Node 26.12.1，Python 3.15.2，锁定 Mihomo 1.19.33，Chromium 156.0.8078.48。
- 测试已构建的 Windows amd64 程序。源码基点 `7118081f4d063cc080bdd7c91cff1757f19a1095`，工作区有未提交改动；精确二进制 SHA256 为 `e7193329e2e538f10100f52824385646293bb16740e2d8599a719725f8051c0d`，不能仅用旧 commit 复现本次构建。
- 每档独立加密 SQLite、独立密钥、随机环回端口和合成 OIDC；不改当前验收数据，不访问真实订阅。应用、压力驱动、测试 IdP 同机运行，桌面其他进程未隔离。
- 每档连续执行 20 次“修改订阅前缀 → 保存 → 真实 Mihomo 检查 → 发布”，历史从 0 增至 20；事务分位数反映这一增长过程，并非固定 20 版本下的纯稳态样本。
- 建立设备、预热下载，等待 5 秒；之后在 20 个发布版本下串行读取管理状态 20 次，分别以 1、10、30 并发执行 200 次完整下载。总计 1,800 次下载，每次核对 SHA256 一致性。
- 时间包含 HTTP 连接和响应体读取。使用 Python urllib、新连接、闭环并发；吞吐量包含驱动端调度开销，属于这次批次观测值，不是服务器理论容量。状态 JSON 解析不计入接口时间。
- P50 为中位数，P95 使用 nearest-rank。20 次事务/状态、10 次页面刷新样本量较小，分位数仅用于本轮比较。没有长期稳态、泄漏、混合读写或生产网络测试。

## 瓶颈判断与优先级

以下是测量现象结合代码阅读的判断，未做 CPU profiler，不能作为精确耗时归因：

1. **优先修复下载路径。** `internal/configuration/service.go` 的 `Download` 持有 Service 全局互斥锁，读取并解密全部设备，然后加载包含草稿和全部发布的整个配置文档，最后才选择当前工件。`storage.Load` 会解密并反序列化整个聚合对象。配置和历史增长会使每次下载成本增加，全局锁又使下载串行排队；与本次并发不增吞吐的现象相符。建议按 token 摘要查询设备，独立读取当前不可变工件，缩短锁范围，并保留每次下载的即时授权检查。
2. **管理状态只返回当前编辑所需数据。** `internal/server/editor.go` 的 state 路由返回全部历史配置并生成两份 YAML。10,000 条时一次响应 15,301,630 字节。建议历史列表只给元数据，选中版本时按需获取；完整 YAML / 差异按需生成。
3. **减少保存时重复写全部历史。** 当前草稿与 20 个版本位于一个加密聚合文档中，保存会重写整个对象。建议分离草稿、不可变发布记录与活动指针，仍通过事务保证发布原子性；不增加用户操作和产品概念。
4. 修改后用同一二进制标识、数据规模、历史数量和驱动复测，并补充“下载同时保存/暂停设备”的混合负载。当前没有预先约定性能 SLA；普通家庭可继续人工试用，但不建议把大规则集同步刷新体验判为通过。
