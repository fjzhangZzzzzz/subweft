# 开发

当前仓库是已确认的设计基线，没有应用代码、安装命令或可运行镜像。先读[设计](design.md)、[架构](architecture.md)、[支持矩阵](support-matrix.md)和[验收标准](acceptance.md)。

## 实现顺序

1. 固定候选Mihomo版本及来源，建立逐字段能力清单、虚构输入和迁移语义对照，不把目标清单误写成已支持。
2. 实现类型化领域模型、持久化迁移、密钥和安全来源解析；以可重复的错误与恢复场景验证边界。
3. 实现方案编译、引用检查、独立内核校验、不可变资源和原子发布/回滚。
4. 实现设备凭据、资源授权、OIDC角色与API，再接入完整表单和端到端测试。
5. 测量资源和并发，制作已锁定的双架构运行工件，进行实际恢复及本机客户端验收。
6. 部署方使用独立实例和真实配置副本验证，形成准确的切换和退役方案后再部署。

这些步骤服务于一个完整首版，不改变已确认的全表单及当前有效能力保留门槛。

## 当前可执行检查

需要Git和Python 3.10以上，不需要额外Python依赖：

```sh
python tools/check_docs.py
git diff --check
```

检查器核对Git索引中的文档链接、文本编码、被误跟踪的运行文件和链接文件。它不联网，不是秘密扫描或公开审计的替代品。应用测试在相关模块实现时增加，避免创建只验证未来占位实现的测试。

## 贡献与工件

使用小而完整的提交，说明行为变化、验证及限制。新增依赖固定版本，记录许可和长期调用方。原始运行结果、数据库、真实导入、性能采样和临时脚本不进入主线。

真实源配置只能在受限实例处理；公共测试使用reserved域名与文档IP。公开前检查整个待提交树和新增历史，不依赖gitignore替代审查。不导入旧Git历史、机密、主机清单或已结束的验证输出。

构建和发布流程应绑定已提交源码、锁定依赖、摘要及明确版本。开发期间无隐式生产更新、自动证书申请或防火墙变更。CI只使用免费额度，不自动升级为付费资源。

## 上游参考

- [Mihomo发行](https://github.com/MetaCubeX/mihomo/releases)：选择并固定版本和架构工件，不能使用运行时latest。
- [Mihomo v1.19.33](https://github.com/MetaCubeX/mihomo/releases/tag/v1.19.33)：当前设计评估的候选参考，不构成已锁定或通过验证。
- [Pocket ID](https://pocket-id.org/)：首个实际OIDC验收目标，不使产品依赖某个私有实例。
- [Clash Verge Rev URL schemes](https://www.clashverge.dev/guide/url_schemes.html)：导入协议不能推导已完成原配置替换。
